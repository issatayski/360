## 0. Урок: где мы ошиблись (не повторять)

Первая версия проекта ушла в **CLI-конвейер** для *уже готовых* equirect-панорам,
собирающий статический тур на Marzipano **без бэкенда, без подписки, без съёмки
как части продукта** (см. историю git до этого коммита). Это «сборочный станок»,
а паспорт требует **сервис под ключ**: веб-приложение с авторизацией, хранилищем,
оплатой, где съёмка и сборка тура происходят *внутри сервиса*.

Конкретные грабли:
- Считали вход «готовыми панорамами + manifest.json» — на деле вход это **агент со
  смартфоном**, снимающий прямо в приложении.
- Запретили бэкенд (было «чистый статический сайт») — продукту нужен серверный
  слой: auth, БД, хранилище, оплата (у нас — PHP+MySQL на shared-хосте).
- Заранее вложились в tiler/triage/orchestrate до проверки формы продукта.
- Считали Marzipano единственным вьюером и целью. Вьюер — это `<iframe>`-деталь;
  цель — тур по ссылке, оплата и удержание клиента.

Правило: **режем безжалостно**. Первая ценность = снял/загрузил 360 → связал в тур
→ ссылка/встраивание. Всё остальное — потом.

## 1. Что это за продукт

SaaS-платформа, где **риелтор сам, без спецоборудования и почти мгновенно** собирает
виртуальный тур квартиры (связанные 360°-панорамы) и по желанию накладывает
ИИ-дизайн интерьера. Итог — **встраиваемая ссылка** на объявление/сайт агента.

- **Аудитория:** риелторы и агентства недвижимости (старт — рынок Казахстана).
- **Монетизация:** плата за тур / кредиты / подписка агента / подписка агентства
  (см. §6). Доступ к съёмке и сборке — по подписке; тарифы пока **заготовка**.
- **Формат старта:** соло-разработчик, минимальный бюджет, ML покупаем по факту
  использования (не строим свой GPU).

## 2. Два режима съёмки (ядро продукта)

Агент снимает объект прямо в приложении. Есть два пути обработки:

### Режим A — «Мгновенный» (self-serve, как https://360.sifro.kz)
- Съёмка 360 в браузере: **камера + гироскоп**, экранный гид ведёт по кольцам-целям
  (горизонт, вверх, вниз, зенит, надир) до полного покрытия сферы.
- **Склейка на клиенте** (WebGL по известным позам IMU) → equirect сразу.
- Агент **связывает несколько комнат/точек** хотспотами-переходами → готовый тур.
- Выход: тур со встраиваемой ссылкой, мгновенно.
- Плюс: бесплатно по инфраструктуре, мгновенно. Минус: качество склейки «бытовое».

### Режим B — «Профи» (managed, обработка у нас через 3DVista)
- Та же управляемая съёмка, но **сырые кадры + позы уходят на сервер** (PHP →
  `uploads/` + запись в `capture_jobs`) как задание на обработку.
- Мы обрабатываем в **3DVista** (профессиональная сборка/ретушь) — выше качество,
  чистые швы, надир/зенит без штатива.
- Готовый тур возвращается клиенту → он встраивает его к себе на сайт.
- Это премиум-качество за счёт про-обработки (ручной/полуручной пайплайн).

Общее для A и B: **гид съёмки** и формат выгрузки кадров (позы из гироскопа) —
один и тот же. Разница только в том, где и как склеивается.

## 3. Стек (под shared-хостинг LAMP)

> **Важно:** развёртывание — обычный shared-хостинг (cPanel/FTP), исходники
> заливаются вручную. Это **PHP + MySQL + Apache, без Node-процесса и без
> долгоживущих воркеров**. Поэтому стек из паспорта (Next.js + Supabase)
> заменён на LAMP. Next.js SSR / Node-бэкенд НЕ используем (не запустится).

| Слой | Инструмент | Зачем |
|---|---|---|
| Фронтенд | **статический JS/HTML/CSS (PWA)** — vanilla или лёгкий фреймворк со статик-экспортом | грузится с shared-хоста как обычные файлы; PWA = manifest + service worker |
| Гид съёмки | датчик ориентации телефона (`DeviceOrientation`) + `getUserMedia` + экранные подсказки | ровная съёмка без камеры за $$$ |
| Склейка режима A | **WebGL в браузере** (по позам IMU) | работает на клиенте, серверу не нужен GPU/CPU |
| Бэкенд | **PHP** (REST-эндпоинты, curl к внешним API) | стандарт shared-хостинга, ключи API прячем на сервере |
| БД | **MySQL/MariaDB** | пользователи, туры, сцены, хотспоты, кредиты, задания |
| Хранилище | **файловая система хоста** (`uploads/`, вне webroot где нужно) | панорамы, кадры, готовые туры; раздача статикой |
| Авторизация | **PHP-сессии или JWT** | подписка/кредиты гейтят доступ |
| Вьюер тура | **Pannellum / Marzipano** (статика) | стандарт риелторских туров, `<iframe>`-встраивание |
| ИИ по запросу | **Replicate / Fal.ai** (вызов из PHP по HTTPS) | платим центы за генерацию, свой GPU не нужен |
| Виртуальный стейджинг | **SDXL + ControlNet** (через Replicate) | ControlNet держит стены/окна, меняет обстановку |
| Про-обработка (режим B) | **3DVista** (внешний ручной пайплайн) | про-сборка туров премиум-качества |
| «Настоящий 3D» (премиум) | **Gaussian Splatting** (готовый endpoint) | верхний ценовой сегмент, дорого — только премиум |

Правило разделения: тяжёлое (ИИ, splatting, про-склейка) — **внешние сервисы по
API**, не на хосте; продукт (туры, авторизация, оплата, встраивание) — PHP+MySQL;
съёмка и склейка режима A — статика/WebGL в браузере.

**Ограничения shared-хостинга (держать в голове):**
- Нет фоновых воркеров и лимит времени выполнения PHP → долгие операции (ИИ,
  режим B) делаем **асинхронно**: PHP ставит задание в таблицу `*_jobs`, статус
  опрашивается фронтом; тяжёлое считает внешний сервис, не хост.
- Никакой серверной склейки/OpenCV на хосте — не тянет. Режим A = браузер,
  режим B = 3DVista у нас.
- Секреты (ключи Replicate, платёжный, БД) — только в серверном PHP-конфиге вне
  webroot, никогда во фронте.

## 4. Поток данных

```
Агент (PWA-статика на shared-хосте, авторизован по подписке через PHP)
  → Съёмка 360 (камера + гироскоп, гид по кольцам) → кадры + позы IMU
  → Режим A: склейка в браузере (WebGL) → equirect → POST на PHP → uploads/
    Режим B: кадры POST на PHP → uploads/ → запись в capture_jobs
             → мы обрабатываем в 3DVista → готовый тур обратно на хост
  → Связка сцен хотспотами (граф комнат) + initialView  [PHP + MySQL]
  → (опц.) ИИ-стейджинг: PHP → Replicate (curl) → результат в uploads/,
     с пометкой «виртуальная обстановка»
  → Публикация тура: запись в MySQL + раздача статикой + вьюер (Pannellum)
  → Встраиваемая ссылка (<iframe>) в объявление агента
  → (агентствам) аналитика просмотров + лид-захват
```

## 5. Модель данных (черновик, MySQL/MariaDB)

- `users` — агент/агентство, план подписки, остаток кредитов, хеш пароля.
- `tours` — id, владелец, название, статус (draft/processing/published), режим (A/B),
  публичный slug для встраивания.
- `scenes` — принадлежит туру: путь к equirect-файлу в `uploads/`, initialView
  (yaw/pitch/fov), heading, позиция на плане.
- `hotspots` — связи сцена→сцена (переходы) и инфо-точки (детали внутри 360; фаза
  «будущее»).
- `capture_jobs` — для режима B: путь к сырым кадрам + позы, статус обработки
  (queued/processing/done) — опрашивается фронтом.
- `staging_jobs` — задания ИИ-стейджинга (комната, стиль, результат, статус).

Файлы (панорамы, кадры, туры) — на диске хоста в `uploads/`, в БД только пути.
Углы вьюера (yaw/pitch/fov) — **в радианах** (частый источник багов).

## 6. Тарифная сетка (заготовка — уточнить перед запуском)

| Продукт | Цена | Что входит |
|---|---|---|
| Разовый тур (кредит) | 5000 тг | тур из связанных панорам + встраиваемая ссылка |
| Пакет 5 туров | ~22 500 тг | −10% |
| Пакет 10 туров | ~40 000 тг | −20% |
| ИИ-стейджинг (доп) | +1500 тг/комната | 2–3 стиля, пометка «виртуальная обстановка» |
| Подписка агента | ~18 000 тг/мес | 15 туров включено, далее 3500 тг/тур |
| Подписка агентства | ~60 000 тг/мес | 60 туров, брендинг, несколько пользователей |
| Премиум «Настоящий 3D» | 15 000–20 000 тг/объект | Gaussian Splatting для топовых объектов |

Логика: старт на разовой оплате/кредитах; подписку вводим вторым шагом; **обязательно
лимит туров** в подписке, иначе «безлимит» съедает маржу. Удерживает агентство:
встраиваемая ссылка, брендинг, аналитика просмотров, лид-захват.

## 7. Фазы разработки (что считается «готово»)

- **Фаза 0 — Каркас (нед. 1–2).** Статический фронт + PHP-эндпоинты + MySQL
  (auth/tours/scenes) + `uploads/`. Приём готового 360-фото ИЛИ базовая съёмка
  режима A. Pannellum-вьюер. Встраиваемая ссылка. Сборка тура вручную.
  → *Готово: тур смотрится по ссылке, всё крутится на shared-хосте.*
- **Фаза 1 — Продукт (нед. 3–5).** Связка панорам хотспотами, дашборд агента,
  оплата, кредитная модель. → *Готово: агент сам создаёт и продаёт тур.*
- **Фаза 2 — ИИ-стейджинг (нед. 6–8).** Replicate: 2–3 стиля обстановки + пометка.
  → *Готово: «вау»-фича и доп-выручка.*
- **Фаза 3 — Гид/съёмка + режим B.** Управляемая съёмка (оба режима), обработка
  кадров в 3DVista/сервере. → *Готово: съёмка обычным телефоном без готовых 360.*
- **Фаза 4 — Для агентств.** Брендинг, аналитика просмотров, лид-захват. → *Готово:
  основа для подписки агентств.*
- **Фаза 5 — Премиум 3D.** Gaussian Splatting как платный endpoint. → *Верхний сегмент.*
- **Будущее — детали в 360.** Инфо-хотспоты внутри панорамы (метки объектов, описания).

## 8. Инварианты качества тура

- **Бесшовный переход между сценами:** при входе в комнату B взгляд продолжает
  движение из A. yaw сцены B считается из направления стрелки и heading (детали —
  когда появятся heading/план; иначе меню-навигация).
- **Загрузочный шов:** сначала превью (сцена не чёрная), потом полное разрешение,
  префетч связанных сцен в фоне → клик по стрелке = мгновенный переход.
- **Физический шов панорамы:** режим A — качество склейки WebGL; режим B — 3DVista
  чистит швы и надир/зенит (штатив/дырка вверху).

## 9. Границы — чего НЕ делать

- **НЕ строить свой ИИ / GPU-инфраструктуру.** Тяжёлый ML (стейджинг, splatting) —
  покупаем по факту через Replicate/Fal/готовые endpoints.
- **НЕ управлять камерой смартфона на низком уровне.** Работаем через web-API
  (getUserMedia + DeviceOrientation), гид на экране. Никаких нативных SDK на старте.
- **НЕ строить безлимитные подписки.** Всегда лимит туров.
- **НЕ давать ИИ дорисовывать несуществующее** (окна, площади) — только менять
  обстановку. Достоверность объявления = доверие + юридический риск.
- **Всегда помечать виртуальную обстановку** в UI (юр. требование).
- **НЕ тянуть Gaussian Splatting в массовый продукт** — ломает экономику; только
  премиум-эндпоинт.
- **Минимум зависимостей.** Не тащим тяжёлые фреймворки ради фич.

## 10. Открытые вопросы (проверить перед запуском)

1. **Оплата в Казахстане:** Kaspi доминирует, Stripe в KZ ограничен. Проверить
   Kaspi Business / локальные эквайринги — влияет на комиссию (~3%) и UX оплаты.
2. **Юр. пометка стейджинга** — заложить в UI.
3. **Достоверность vs «красота»** — не дорисовывать несуществующее.
4. **Первый канал продаж** — 1–2 лояльных агентства для пилота.
5. **Режим B — 3DVista:** ручной пайплайн на старте? Как передаём кадры и
   возвращаем готовый тур? SLA по срокам обработки?

## 11. Что переиспользовать из старой версии (в истории git)

Старый код удалён из рабочего дерева, но лежит в истории git — доставать по мере
надобности как референс, не как основу:
- `capture/index.html` — UX съёмки (камера+гироскоп, кольца-цели, выгрузка кадров
  с позами). Прямой прототип гида съёмки для фазы 3.
- `app/index.html` — `stitchEquirect()`: WebGL-склейка кадров в equirect по позам
  IMU. Прямой прототип режима A.
- `src/stitch/stitch.py` — склейка на Python (OpenCV) по позам IMU. НЕ для
  shared-хоста (не тянет) — референс, если когда-то автоматизируем режим B на
  отдельном внешнем сервисе.
- `docs/tour/` — рабочий пример вывода вьюера (Marzipano, тайлы).

git log --oneline        # найти коммит со старым кодом
